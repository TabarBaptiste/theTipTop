Technologies et compatibilité
Stack technique retenue
La stack technologique du projet Thé Tip Top a été sélectionnée selon trois critères directeurs : la cohérence full-TypeScript de bout en bout pour garantir la sécurité des types entre le front-end et le back-end, la maintenabilité à long terme dans un contexte de projet à durée de vie limitée mais à données pérennes, et l'intégration fluide avec l'infrastructure CI/CD en cours de déploiement chez Furious Ducks. Chaque choix technologique est justifié ci-dessous par rapport aux alternatives envisagées.
Back-end - API REST
Le back-end de la plateforme repose sur NestJS 10 avec TypeScript comme framework principal. NestJS a été retenu face à Express et Fastify pour sa structure modulaire inspirée d'Angular, qui impose une organisation claire du code en modules indépendants - auth, tickets, utilisateurs, gains, statistiques - facilitant la maintenance et l'évolution du projet. Contrairement à Express ou Fastify qui laissent une liberté totale d'organisation (et donc un risque de dette technique élevé sur un projet multi-développeurs), NestJS impose des conventions qui garantissent la cohérence du code quelle que soit la personne qui intervient. La validation des données entrantes est assurée nativement via class-validator, la documentation API est générée automatiquement via Swagger/OpenAPI, et les tests unitaires sont intégrés avec Jest sans configuration supplémentaire.

La gestion de la base de données est assurée par Prisma comme ORM, connecté à PostgreSQL 16. Prisma a été préféré à TypeORM et Sequelize pour sa génération automatique de types TypeScript à partir du schéma, ce qui élimine toute désynchronisation entre le modèle de données et le code applicatif. Ses migrations automatiques et son schéma déclaratif réduisent considérablement le risque d'erreur humaine lors des évolutions du schéma en production.

Redis remplit quatre rôles distincts dans l'architecture : le cache des statistiques du tableau de bord administrateur avec une invalidation toutes les cinq minutes pour garantir la fraîcheur des données sans surcharger PostgreSQL à chaque rafraîchissement, la gestion des sessions utilisateurs, le rate limiting de l'API avec comptage des requêtes par IP et par utilisateur, et la file d'attente pour la synchronisation asynchrone des contacts vers Brevo en cas d'indisponibilité temporaire de l'API.
Front-end - WebApp
Le front-end est développé avec Next.js 14 en App Router, choisi face à une React SPA classique et à Vue/Nuxt pour deux raisons principales. La première est le SEO : l'opération jeu-concours doit être découvrable sur les moteurs de recherche pendant toute sa durée, ce qui exige un rendu côté serveur (SSR) ou une génération statique (SSG) que Next.js propose nativement, contrairement à une React SPA dont le contenu est invisible aux crawlers. La seconde est la performance : les Server Components de l'App Router permettent de réduire significativement le JavaScript envoyé au navigateur, améliorant les temps de chargement sur mobile - support privilégié de la cible.

Le styling est assuré par TailwindCSS combiné à Shadcn/ui pour les composants d'interface. La gestion de l'état global repose sur Zustand pour sa légèreté et React Query pour la synchronisation des données serveur. Les formulaires sont gérés avec React Hook Form et Zod pour la validation des schémas côté client, en cohérence avec la validation class-validator côté serveur. Les tests end-to-end sont réalisés avec Cypress, qui simule les parcours utilisateurs complets depuis l'inscription jusqu'à la soumission d'un ticket.
Infrastructure
L'infrastructure repose sur Docker et Docker Compose pour la containerisation de l'ensemble des services - API, base de données, Redis, front-end - garantissant la parité entre les environnements de développement, de staging et de production. Le reverse proxy est assuré par Traefik avec certificat SSL Let's Encrypt pour le chiffrement TLS automatique. Le monitoring est assuré par le couple Prometheus et Grafana, qui permettent de surveiller les métriques clés de l'application en temps réel - taux de requêtes, temps de réponse, utilisation mémoire - et de configurer des alertes en cas de dépassement de seuils critiques. Le workflow CI/CD s'appuie sur Jenkins, outil standard de Furious Ducks, pour l'automatisation des phases de test, de build et de déploiement.

L'objectif est de couvrir plus de 95% des navigateurs effectivement utilisés par cette cible tout en conservant la liberté d'utiliser les fonctionnalités CSS et JavaScript modernes nécessaires à la qualité de l'expérience visuelle.

Software
La conduite du projet Thé Tip Top mobilise un ensemble d'outils couvrant quatre domaines distincts : la gestion de projet, la conception graphique, le développement technique et les audits qualité. Le choix de chaque outil résulte d'une décision délibérée fondée sur sa pertinence pour le contexte du projet, sa compatibilité avec les autres outils de la stack et son alignement avec les pratiques internes de Furious Ducks.
Gestion de projet
La coordination de l'équipe et le suivi de l'avancement reposent sur trois outils complémentaires. Notion est utilisé comme espace de travail collaboratif centralisé : il héberge la documentation du projet, le backlog Scrum, les comptes-rendus de réunion et la répartition des tâches entre les membres de l'équipe. Sa flexibilité et sa prise en main rapide en font un outil adapté à une équipe de trois personnes travaillant en méthode Scrum. GanttProject assure la planification temporelle du projet sous forme de diagramme de Gantt en mode ASAP, permettant de visualiser les dépendances entre tâches, les jalons clés et les ressources mobilisées à chaque phase. GitLab est l'outil central de gestion de versions du projet : il héberge les dépôts de code source, gère les merge requests et les revues de code, et s'intègre directement avec Jenkins pour déclencher les pipelines CI/CD automatisés conformément au workflow défini pour Furious Ducks. L'ensemble de ces outils garantit la traçabilité complète des évolutions du projet, la coordination asynchrone de l'équipe et le respect des délais de livraison.
Conception graphique
La dimension visuelle du projet est traitée avec deux outils principaux. Figma est l'outil central de conception UI/UX : il permet la création des maquettes fonctionnelles basse et haute fidélité, le prototypage interactif des parcours utilisateurs et la collaboration en temps réel entre le designer et la cheffe de projet pour les validations. Les maquettes produites dans Figma constituent la référence visuelle transmise au développeur pour l'intégration front-end, réduisant les allers-retours d'interprétation. La Suite Adobe - Illustrator pour la création vectorielle et Photoshop pour le traitement des visuels photographiques - est utilisée pour la création du nouveau logo de Thé Tip Top, ses déclinaisons sur différents supports et les éléments de la charte graphique nécessitant une précision vectorielle que Figma ne permet pas nativement. L'ensemble de ces outils assure la cohérence graphique sur la totalité des supports du projet, du site web aux documents imprimés en boutique.
Développement technique
L'environnement de développement est standardisé sur Visual Studio Code, éditeur retenu pour sa légèreté, son écosystème d'extensions riche - ESLint, Prettier, Prisma, Docker - et sa compatibilité native avec TypeScript. Node.js constitue le runtime d'exécution du back-end NestJS, dans sa version LTS pour garantir la stabilité en production. Docker et Docker Compose assurent la containerisation de l'ensemble des services du projet - API, base de données PostgreSQL, Redis, front-end Next.js - garantissant la parité stricte entre les environnements de développement local, de staging et de production, et éliminant les problèmes de configuration spécifiques à chaque poste de travail. PostgreSQL 16 est le système de gestion de base de données relationnelle retenu, Redis assure la couche de cache et de gestion des files d'attente, et Jenkins orchestre les pipelines d'intégration et de déploiement continus. Postman est utilisé pour les tests manuels des endpoints de l'API REST lors des phases de développement, en complément des tests automatisés. Git assure la gestion de version locale avant synchronisation avec GitLab.
Audits et outils d'analyse
La qualité technique et la conformité aux standards professionnels sont vérifiées par quatre outils d'audit complémentaires. SEMrush est utilisé pour l'audit SEO initial et l'analyse de la concurrence en ligne : il permet d'identifier les mots-clés pertinents pour le jeu-concours, d'analyser les pratiques SEO des concurrents et de mesurer la progression du référencement naturel de la plateforme pendant la durée de l'opération. Google Lighthouse est l'outil d'audit de performance et d'accessibilité retenu pour sa gratuité, son intégration native dans Chrome DevTools et la fiabilité de ses métriques Core Web Vitals - LCP, FID, CLS - qui sont les indicateurs de référence de Google pour évaluer la qualité de l'expérience utilisateur. Le Contrast Color Analyzer permet de vérifier la conformité des contrastes de couleurs entre le texte et le fond selon les critères WCAG niveau AA, garantissant l'accessibilité visuelle de la plateforme pour les utilisateurs malvoyants. PageSpeed Insights complète Google Lighthouse en fournissant une analyse des performances sur des données de terrain réelles collectées par Google, permettant de distinguer les performances mesurées en laboratoire des performances effectivement perçues par les utilisateurs finaux.
L'ensemble de ces audits est réalisé de manière systématique à l'issue de chaque sprint de développement et avant chaque mise en production, garantissant la conformité continue de la plateforme aux bonnes pratiques SEO, aux exigences d'accessibilité WCAG, aux standards de performance web et aux engagements RSE de Thé Tip Top en matière de sobriété numérique.
Tests applications
La qualité d'une plateforme gérant 500 000 codes uniques, des données personnelles soumises au RGPD et des opérations d'écriture concurrentes ne peut pas reposer uniquement sur des vérifications manuelles en phase de recette. Une stratégie de tests automatisés structurée et intégrée au pipeline CI/CD est la garantie que chaque évolution du code est validée de manière systématique, reproductible et traçable, sans dépendre de la disponibilité ou de la vigilance humaine.
La stratégie retenue pour le projet Thé Tip Top s'articule autour de quatre niveaux complémentaires, organisés selon la pyramide des tests : les tests unitaires constituent la base, les plus nombreux et les plus rapides à exécuter ; les tests d'intégration vérifient la cohérence entre les composantes du système ; les tests fonctionnels end-to-end valident les parcours utilisateurs complets ; et les tests de performance s'assurent que la plateforme résiste aux charges réelles de l'opération. L'ensemble de ces niveaux est intégré au pipeline CI/CD Jenkins de Furious Ducks, garantissant qu'aucune régression ne peut atteindre l'environnement de production sans avoir été détectée en amont.
Tests unitaires
Les tests unitaires constituent le premier niveau de la stratégie et le plus fondamental. Leur objectif est de vérifier le bon fonctionnement de chaque composant applicatif de manière strictement isolée, en s'affranchissant de toute dépendance externe - base de données, API tierce, système de fichiers - grâce à l'utilisation de mocks et de stubs. Ce niveau de test est le plus rapide à exécuter et celui qui offre le retour d'information le plus immédiat au développeur : une régression introduite dans un service NestJS est détectée en quelques secondes sans nécessiter de démarrer l'ensemble de l'infrastructure.
Les composants couverts par les tests unitaires incluent l'ensemble des services NestJS - service d'authentification, service de gestion des tickets, service de calcul des gains, service de statistiques - ainsi que la logique métier critique : génération et validation des tokens JWT, vérification du format des codes tickets, calcul des pourcentages de répartition des lots et fonctions utilitaires côté front-end. Une attention particulière est portée aux branches conditionnelles de la logique de soumission de ticket, dont la couverture exhaustive est indispensable pour garantir l'intégrité du jeu.
Les tests unitaires sont écrits avec Jest, intégré nativement à NestJS et configuré sans effort supplémentaire. Pour les composants front-end React nécessitant une vérification de rendu, React Testing Library complète Jest en permettant de tester les composants depuis le point de vue de l'utilisateur plutôt que depuis les détails d'implémentation, ce qui produit des tests plus robustes aux refactorisations.
Sur le plan de l'intégration au pipeline CI/CD, les tests unitaires sont exécutés automatiquement à chaque push sur une branche de développement et à chaque ouverture de Merge Request sur GitLab, avant toute autre étape du pipeline. Un rapport de couverture est généré au format LCOV et XML à l'issue de chaque exécution. Ce rapport est transmis automatiquement à SonarQube pour analyse de la qualité du code et archivé dans Jenkins pour historisation. Un seuil minimum de couverture de 80 % est défini comme condition de passage du pipeline : en dessous de ce seuil, le build est marqué en échec et le déploiement est bloqué.
Les tests unitaires remplissent trois fonctions essentielles dans la durée du projet. Ils limitent les régressions en signalant immédiatement toute modification du comportement attendu d'un composant. Ils sécurisent les évolutions fonctionnelles en donnant aux développeurs la confiance nécessaire pour refactoriser du code existant sans craindre d'introduire des bugs silencieux. Et ils constituent un socle de stabilité indispensable avant l'exécution des niveaux de tests supérieurs, garantissant que les tests d'intégration ne sont pas pollués par des bugs unitaires non détectés.
Tests d’intégration
Les tests unitaires valident chaque composant en isolation, mais ils ne peuvent pas détecter les erreurs qui n'apparaissent que lorsque plusieurs composantes du système interagissent entre elles. C'est précisément le rôle des tests d'intégration : vérifier que les contrats entre les différentes couches de l'application sont respectés dans des conditions proches de la réalité, avec de vraies connexions à la base de données et au cache, sans recourir à des mocks qui masqueraient les problèmes d'intégration réels.
Quatre périmètres d'intégration sont couverts par ce niveau de tests. Le premier est l'intégration entre l'API NestJS et PostgreSQL : chaque endpoint qui effectue des opérations de lecture ou d'écriture en base est testé avec une vraie instance PostgreSQL pour vérifier que les requêtes SQL générées par Prisma sont correctes, que les contraintes d'intégrité sont respectées et que les transactions atomiques se comportent comme attendu - notamment le mécanisme SELECT FOR UPDATE de la soumission de ticket. Le deuxième périmètre est l'intégration entre l'API et Redis : les comportements de cache, d'expiration des sessions et de rate limiting sont vérifiés avec une instance Redis réelle pour s'assurer que les règles de gestion sont correctement appliquées. Le troisième périmètre couvre l'authentification dans son ensemble - génération et validation des tokens JWT, flux OAuth2 Google et Facebook, expiration des sessions - en conditions réelles plutôt que mockées. Le quatrième périmètre vérifie le bon fonctionnement des guards NestJS sur toutes les routes protégées, en s'assurant qu'un utilisateur non authentifié ou disposant d'un rôle insuffisant reçoit bien un HTTP 403 et ne peut pas accéder aux ressources qui lui sont interdites.
La mise en œuvre repose sur l'instanciation d'une base de données PostgreSQL isolée dans un conteneur Docker dédié aux tests, alimentée par des données de test reproductibles et réinitialisées avant chaque suite de tests pour garantir l'indépendance des scénarios entre eux. Cette isolation stricte évite toute contamination entre les données de test et les données de l'environnement de staging. Les tests sont écrits et exécutés avec Jest, en utilisant le module de test intégré de NestJS qui permet de démarrer une instance complète de l'application dans un contexte contrôlé.
Dans le pipeline CI/CD, les tests d'intégration sont déclenchés automatiquement après la validation complète des tests unitaires, garantissant que les composants individuels sont sains avant de tester leurs interactions. Tout échec bloque immédiatement la suite du pipeline et empêche le déploiement vers l'environnement de staging, quelle que soit la nature de l'erreur détectée. Les rapports d'exécution sont consolidés dans SonarQube aux côtés des rapports de tests unitaires, offrant une vision unifiée de la qualité du code, et archivés dans Jenkins pour historisation et analyse des tendances sur la durée du projet.
Les tests d'intégration permettent de détecter une catégorie d'erreurs particulièrement difficile à identifier autrement : les erreurs SQL silencieuses générées par une mauvaise configuration de Prisma, les problèmes de configuration des connexions Redis en environnement conteneurisé, les défauts d'intégration entre la couche de cache et la logique applicatif qui n'apparaissent que sous certaines conditions de timing, et les mauvaises interactions entre services qui semblent fonctionner correctement en isolation mais échouent lorsqu'ils sont confrontés aux contraintes réelles du système.
Tests fonctionnels (end-to-end)
Les tests unitaires et d'intégration valident respectivement les composants isolés et leurs interactions techniques, mais aucun de ces deux niveaux ne peut garantir que l'expérience vécue par un utilisateur réel sur la plateforme est conforme aux attentes fonctionnelles. C'est le rôle des tests end-to-end : simuler le comportement d'un utilisateur humain interagissant avec l'interface graphique dans un navigateur réel, en vérifiant que les parcours critiques fonctionnent de bout en bout, de la première action visible jusqu'à la persistance du résultat en base de données.
Les parcours couverts par les tests E2E correspondent aux flux fonctionnels les plus critiques de la plateforme, identifiés lors de l'analyse des cas d'utilisation. Le parcours de création de compte et de connexion vérifie l'ensemble du tunnel d'inscription - remplissage du formulaire, validation RGPD, réception de l'e-mail de confirmation, connexion par email et par Social Login Google et Facebook. Le parcours de participation au jeu-concours est le plus critique : il simule la saisie d'un code ticket valide, vérifie l'affichage correct du gain associé et contrôle la mise à jour du statut du ticket en base. Le parcours de consultation des gains vérifie que l'historique des participations est correctement affiché dans l'espace personnel du client. Le parcours administrateur couvre l'accès au tableau de bord, la visualisation des statistiques en temps réel et le déclenchement du tirage au sort. Enfin, le parcours employé boutique vérifie la recherche d'un client, la validation de la remise d'un lot et l'horodatage correct de l'opération.
L'outil retenu pour les tests E2E est Cypress, choisi pour sa robustesse sur les applications React et Next.js, sa capacité à intercepter et mocker les requêtes réseau pour isoler les scénarios de test des services tiers comme Brevo et Google Analytics, et sa génération automatique de captures d'écran et de vidéos en cas d'échec - un atout considérable pour le débogage à distance. Postman couplé à Newman est utilisé en complément pour les tests des endpoints de l'API REST de manière automatisée, permettant de valider les contrats d'API indépendamment de l'interface graphique et de détecter les régressions sur les codes HTTP retournés, les formats de réponse et les règles de validation.
Dans le pipeline CI/CD, les tests E2E occupent une position stratégique : ils sont exécutés exclusivement sur l'environnement de staging, qui réplique fidèlement la configuration de production avec des données de test représentatives. Leur exécution est déclenchée automatiquement après la réussite des tests d'intégration et constitue la condition obligatoire et non contournable avant toute promotion vers l'environnement de production. Tout échec d'un test E2E bloque immédiatement le pipeline et déclenche une notification à l'équipe de développement avec le rapport d'erreur complet. Cette règle sans exception garantit qu'aucune régression sur les parcours utilisateurs critiques ne peut atteindre les utilisateurs finaux.
Les rapports sont générés automatiquement au format HTML à l'issue de chaque exécution, incluant le résultat de chaque test, les captures d'écran prises aux étapes clés des parcours et les captures vidéo intégrales des tests ayant échoué. Ces rapports sont archivés dans Jenkins pour constituer un historique de la qualité fonctionnelle du projet sur la durée, et transmis à la cheffe de projet pour validation avant chaque mise en production. Les tests E2E remplissent ainsi trois fonctions complémentaires dans la stratégie qualité globale : ils valident que les parcours utilisateurs réels fonctionnent conformément aux cas d'utilisation définis dans la section E, ils garantissent la cohérence entre le front-end et le back-end en conditions réelles, et ils réduisent considérablement le risque d'incidents en production en détectant les régressions dans un environnement contrôlé avant qu'elles n'impactent les participants au jeu-concours.
Qualité du code - SonarQube
Les tests automatisés garantissent que le code fonctionne correctement, mais ils ne disent rien sur la qualité intrinsèque du code lui-même : sa lisibilité, sa maintenabilité, sa sécurité et l'absence de dette technique accumulée. C'est le rôle de SonarQube : fournir une analyse statique continue et objective du code source, indépendamment de son comportement à l'exécution, pour détecter les problèmes de qualité avant qu'ils ne deviennent des problèmes de production.
La version Community Edition de SonarQube est retenue pour ce projet. Elle couvre l'ensemble des besoins identifiés sur une stack TypeScript et JavaScript sans nécessiter de licence commerciale, ce qui est cohérent avec les valeurs open source de Furious Ducks. SonarQube remplit cinq rôles distincts dans la stratégie qualité du projet. L'analyse statique du code TypeScript et JavaScript détecte les bugs potentiels, les mauvaises pratiques et les constructions de code dangereuses sans exécuter le programme - par exemple une variable potentiellement undefined utilisée sans vérification, ou une promesse non gérée qui pourrait provoquer un crash silencieux en production. La détection des vulnérabilités de sécurité identifie les failles connues dans le code applicatif : injections, exposition de données sensibles, mauvaise gestion des secrets. L'analyse de la complexité cyclomatique signale les fonctions trop complexes qui sont statistiquement plus susceptibles de contenir des bugs et plus difficiles à tester exhaustivement. La détection des duplications de code identifie les portions de code répétées qui devraient être factorisées pour réduire la surface de maintenance. Enfin, la consolidation de la couverture de tests agrège les rapports LCOV générés par les tests unitaires et d'intégration pour produire une vision unifiée du taux de couverture global du projet.
La fonctionnalité la plus importante de SonarQube dans le contexte de ce projet est la mise en place de quality gates - des seuils de qualité configurables dont le non-respect bloque automatiquement la progression dans le pipeline CI/CD. Les seuils définis pour le projet Thé Tip Top sont les suivants : couverture de tests minimale de 80 % sur le nouveau code, zéro nouvelle vulnérabilité de sécurité de niveau critique ou bloquant, taux de duplication inférieur à 3 % et note de maintenabilité minimale de A sur les nouveaux fichiers. Ces seuils sont vérifiés automatiquement après chaque build et exécution des tests, et leur non-respect bloque immédiatement le pipeline avant tout déploiement vers les environnements de staging ou de production.
SonarQube est également intégré directement dans l'environnement de développement via le plugin SonarLint pour Visual Studio Code, qui remonte les problèmes de qualité en temps réel pendant l'écriture du code, sans attendre l'exécution du pipeline. Cette intégration en amont du cycle de développement est particulièrement précieuse : corriger un problème de qualité au moment où il est introduit est significativement moins coûteux que de le détecter lors d'une revue de code ou, pire, en production.
Les rapports produits par SonarQube sont accessibles via un dashboard projet dédié qui présente l'évolution de la qualité du code au fil des sprints : progression de la couverture de tests, réduction de la dette technique, historique des vulnérabilités détectées et corrigées. Ces rapports sont exportables au format PDF et CSV pour intégration dans les comptes-rendus de sprint et les reportings transmis à la direction de Thé Tip Top. Ils constituent également une pièce de la documentation technique remise au client à la livraison du projet, attestant de la qualité du code produit par Furious Ducks.
Tests de performance
Les tests fonctionnels valident que la plateforme se comporte correctement pour un utilisateur unique dans des conditions nominales. Ils ne répondent pas à la question critique pour ce projet : que se passe-t-il lorsque plusieurs milliers d'utilisateurs accèdent simultanément à la plateforme, notamment lors des pics de trafic générés par les campagnes d'activation des influenceurs partenaires ? Une plateforme qui fonctionne parfaitement en isolation mais s'effondre sous charge constituerait un échec opérationnel majeur, potentiellement irréversible pour la réputation de Thé Tip Top auprès de sa communauté. Les tests de performance sont donc la dernière ligne de défense avant la mise en production.
L'outil retenu est K6 de Grafana, choisi pour trois raisons principales. Sa syntaxe JavaScript permet aux développeurs de l'équipe de rédiger les scénarios de test sans apprentissage d'un nouveau langage. Son architecture en ligne de commande s'intègre nativement dans le pipeline Jenkins sans dépendances supplémentaires. Et sa compatibilité native avec Grafana permet de visualiser les résultats en temps réel dans le tableau de monitoring déjà en place pour la supervision de l'infrastructure.
Cinq types de tests sont réalisés avec K6. Le test de montée en charge simule une augmentation progressive du nombre d'utilisateurs simultanés - de 10 à 500 en l'espace de dix minutes - pour identifier le seuil à partir duquel les temps de réponse se dégradent et les premiers goulots d'étranglement apparaissent. Le test de charge soutenue maintient un niveau de trafic constant correspondant à l'usage nominal prévu pendant trente minutes, pour détecter les dégradations progressives liées à des fuites mémoire ou à une saturation progressive du pool de connexions PostgreSQL. Le test de pic simule l'afflux massif et soudain de visiteurs correspondant à une activation influenceur - plusieurs centaines de connexions simultanées en moins d'une minute - pour vérifier que le système de cache Redis absorbe correctement la charge sans répercuter les requêtes sur PostgreSQL. Le test de stress pousse délibérément la plateforme au-delà de ses limites pour identifier son point de rupture et vérifier qu'elle se dégrade gracieusement plutôt que de s'effondrer brutalement. Enfin, le test de récupération vérifie que la plateforme revient à un état nominal dans un délai acceptable après un pic de charge intense.
Les métriques clés mesurées à l'issue de chaque test sont les percentiles p95 et p99 des temps de réponse - c'est-à-dire les temps de réponse en dessous desquels se situent respectivement 95 % et 99 % des requêtes - plutôt que la moyenne, qui masque les valeurs extrêmes. Les seuils d'acceptabilité définis pour le projet sont les suivants : temps de réponse p95 inférieur à 500 millisecondes pour les endpoints critiques de soumission de ticket, taux d'erreur inférieur à 1 % sous charge nominale et temps de réponse p99 inférieur à deux secondes pour l'ensemble des endpoints de la plateforme. Tout dépassement de ces seuils lors des tests de performance en staging déclenche une analyse des goulots d'étranglement avant toute promotion vers la production.
Dans le pipeline CI/CD, les tests de performance sont exécutés en environnement de staging après la validation complète des tests E2E, et leur rapport constitue une condition obligatoire à la validation de mise en production. Les résultats sont exportés au format JSON pour archivage dans Jenkins et visualisés en temps réel dans Grafana, où un dashboard dédié aux tests de charge permet de comparer les performances entre les différents sprints et d'identifier les régressions de performance introduites par les évolutions du code. Cette historisation des métriques de performance sur la durée du projet constitue également un élément de preuve remis au client à la livraison, attestant que la plateforme a été validée pour les niveaux de charge attendus lors de l'opération.
Bonnes pratiques
La stratégie de tests mise en place pour le projet Thé Tip Top ne se résume pas à une collection d'outils : elle repose sur un ensemble de principes organisationnels qui en garantissent l'efficacité et la pérennité sur la durée du projet.
Le premier principe est le respect de la pyramide des tests. La grande majorité des tests est constituée de tests unitaires, rapides à exécuter et peu coûteux à maintenir. Les tests d'intégration et E2E, plus lents et plus fragiles par nature, sont moins nombreux mais couvrent les flux les plus critiques. Cette répartition n'est pas arbitraire : elle optimise le rapport entre le temps d'exécution du pipeline et la confiance apportée par les tests. Un pipeline composé majoritairement de tests E2E serait trop lent pour être exécuté à chaque push, ce qui inciterait les développeurs à le contourner. Un pipeline majoritairement unitaire ne détecterait pas les problèmes d'intégration. L'équilibre de la pyramide est donc un choix délibéré de productivité autant que de qualité.
Le deuxième principe est l'isolation stricte des environnements de test via Docker. Chaque niveau de test s'exécute dans un environnement containerisé indépendant, avec sa propre instance de base de données et de cache, réinitialisée avant chaque suite de tests. Cette isolation garantit que les tests sont reproductibles et indépendants entre eux, qu'ils produisent le même résultat quelle que soit la machine sur laquelle ils s'exécutent et quelle que soit l'heure à laquelle ils sont lancés. Elle élimine également le risque de contamination entre les données de test et les données réelles de staging ou de production.
Le troisième principe est le blocage automatique et non contournable du pipeline en cas d'échec à n'importe quel niveau. Aucune dérogation manuelle n'est possible : un test qui échoue arrête le pipeline, point. Cette règle sans exception peut sembler contraignante, mais elle est la seule garantie réelle que les tests jouent leur rôle de filet de sécurité. Un pipeline dont les échecs peuvent être ignorés n'est pas un pipeline de qualité, c'est une suggestion.
Le quatrième principe est la mise en place de quality gates SonarQube comme condition obligatoire de promotion entre les environnements. Ces seuils objectifs et mesurables dépolitisent les décisions de mise en production : ce n'est plus une question d'appréciation subjective de la qualité du code, mais une vérification automatique de critères définis en amont et acceptés par l'ensemble de l'équipe et du client.
Le cinquième principe est la validation des performances en staging avant toute mise en production. Aucune version de la plateforme ne peut être déployée en production sans avoir été soumise aux tests de charge K6 et sans avoir satisfait aux seuils de performance définis. Ce principe est particulièrement critique dans le contexte d'une opération de jeu-concours où les pics de trafic sont prévisibles et où une indisponibilité de la plateforme lors d'une activation influenceur aurait un impact direct et immédiat sur la réputation de Thé Tip Top.
Hébergement et nom de domaine
Nom de domaine
Le choix du nom de domaine et de l'architecture de nommage est une décision qui engage à la fois la cohérence de marque, la stratégie SEO et l'organisation technique de l'infrastructure. Deux niveaux de nommage sont préconisés pour le projet Thé Tip Top.
Le domaine principal retenu est www.thetiptop.fr. L'extension .fr est privilégiée pour plusieurs raisons convergentes : elle renforce la crédibilité et l'ancrage local de la marque auprès d'une clientèle française, elle bénéficie d'une autorité de domaine reconnue par les algorithmes de Google pour le référencement naturel en France, et elle est cohérente avec le positionnement premium et artisanal de l'enseigne, qui ne cherche pas à se projeter immédiatement sur un marché international. Son coût d'enregistrement et de renouvellement annuel est estimé entre 10 et 15 € HT auprès d'un registrar accrédité comme OVH ou Gandi, ce qui en fait une dépense négligeable au regard de sa valeur stratégique.
Le sous-domaine jeu.thetiptop.fr est dédié à l'opération jeu-concours. Ce choix architectural présente trois avantages distincts. Sur le plan technique, il permet d'isoler complètement l'infrastructure du jeu-concours de celle du site principal : les serveurs, les bases de données et les configurations sont indépendants, ce qui signifie qu'un incident technique sur le jeu-concours n'impacte pas la disponibilité du site principal, et inversement. Sur le plan SEO, un sous-domaine dédié à une opération temporaire évite de polluer l'autorité du domaine principal avec des pages à durée de vie limitée qui seront désindexées à la clôture de l'opération. Sur le plan de la cohérence de marque, le préfixe "jeu" est immédiatement compréhensible par les participants et mémorisable, facilitant la communication sur les supports physiques en boutique et sur les réseaux sociaux.
La sécurisation des communications est assurée par un certificat SSL Let's Encrypt, autorité de certification gratuite et reconnue par l'ensemble des navigateurs modernes. Le certificat est généré et renouvelé automatiquement par Traefik, le reverse proxy retenu dans l'infrastructure, sans intervention manuelle. Let's Encrypt délivre des certificats d'une validité de 90 jours avec renouvellement automatique déclenché 30 jours avant expiration, garantissant qu'aucune interruption du chiffrement HTTPS ne peut survenir pendant la durée de l'opération. Ce choix est également cohérent avec la démarche RSE et de sobriété numérique du projet : recourir à une solution gratuite et automatisée plutôt qu'à un certificat commercial payant réduit les coûts sans compromis sur la sécurité.
Hébergement Cloud préconisé
Le choix de la solution d'hébergement est directement conditionné par les contraintes techniques et opérationnelles du projet. La gestion de 500 000 codes uniques en base de données, les pics de trafic imprévisibles liés aux activations d'influenceurs partenaires et l'exigence de haute disponibilité pendant toute la durée de l'opération rendent impossible le recours à un hébergement mutualisé. Sur un hébergement mutualisé, les ressources serveur sont partagées entre plusieurs clients : un pic de trafic sur la plateforme Thé Tip Top pourrait être étranglé par le prestataire pour protéger les autres clients, ou inversement, un voisin consommant beaucoup de ressources pourrait dégrader les performances de la plateforme à un moment critique. Ce risque est inacceptable dans le contexte d'une opération marketing à durée de vie limitée où chaque heure d'indisponibilité se traduit par une perte directe de participants et un impact négatif sur la réputation de la marque.
La solution préconisée est un hébergement sur instance Public Cloud OVHcloud, prestataire français retenu pour quatre raisons convergentes. Premièrement, ses datacenters sont localisés en Europe, ce qui garantit que les données personnelles des participants - collectées dans le cadre du RGPD - ne transitent pas hors du territoire européen, condition indispensable à la conformité réglementaire. Deuxièmement, OVHcloud offre un rapport performance/prix particulièrement compétitif sur le marché de l'hébergement cloud français, notamment face à AWS ou Google Cloud dont les tarifs sont significativement plus élevés pour des performances équivalentes sur ce type de charge. Troisièmement, le support natif de Linux et de Docker garantit une compatibilité totale avec l'infrastructure containerisée définie pour le projet. Quatrièmement, la flexibilité du Public Cloud OVHcloud permet une montée en charge temporaire des ressources pendant la période de forte affluence, puis un redimensionnement à la baisse après la clôture de l'opération, optimisant ainsi le coût total d'hébergement sur la durée du projet.
La configuration d'instance recommandée est la suivante : 4 à 8 vCPU pour absorber les pics de traitement liés aux soumissions simultanées de codes, 8 à 16 Go de RAM pour maintenir en cache les statistiques fréquemment consultées et les sessions Redis actives, 160 Go de stockage SSD NVMe minimum pour garantir des temps d'accès disque compatibles avec les exigences de performance de PostgreSQL sous charge, et une bande passante d'au moins 500 Mbps pour absorber les afflux de trafic lors des activations influenceurs. Le contrat de niveau de service retenu est un SLA d'au moins 99,9 %, ce qui correspond à une indisponibilité maximale tolérée de 8,7 heures sur l'année, soit moins de 44 minutes sur la durée de 30 jours de l'opération.
Le coût d'hébergement est estimé entre 80 et 120 € HT par mois pendant la période active du jeu-concours. Cette fourchette intègre le coût de l'instance principale, du stockage SSD et de la bande passante consommée. Après la clôture de la période de réclamation, les ressources sont redimensionnées à la baisse vers une instance minimale pour la phase d'archivage des données, réduisant le coût mensuel à moins de 20 € HT jusqu'à la suppression complète des données conformément aux obligations RGPD. Cette stratégie de downscaling progressif est une application directe des engagements de sobriété numérique et de maîtrise des coûts portés par Furious Ducks dans la conduite de ce projet.
Stratégie de sauvegarde
La stratégie de sauvegarde est l'un des livrables explicitement identifiés dans la transformation de Furious Ducks, et elle prend une dimension particulièrement critique dans le contexte du projet Thé Tip Top. La base de données des participants et des gains représente un actif irremplaçable : en cas de perte, il serait impossible de reconstituer les 500 000 codes pré-attribués, l'historique des participations et les consentements RGPD horodatés, avec des conséquences légales et réputationnelles potentiellement graves pour Thé Tip Top. La stratégie de sauvegarde n'est donc pas une précaution accessoire - c'est une obligation contractuelle et légale.
Périmètre des sauvegardes
Trois catégories de données sont couvertes par la stratégie de sauvegarde. La base de données PostgreSQL constitue le périmètre le plus critique : elle contient les données des participants, les codes tickets avec leur statut d'utilisation, les gains associés, les consentements RGPD horodatés et le résultat du tirage au sort final. Les fichiers applicatifs - code source déployé, assets statiques, fichiers de configuration des services - sont sauvegardés pour permettre une restauration complète de la plateforme en cas de défaillance majeure. Les configurations serveur - paramètres Traefik, variables d'environnement, configurations Docker Compose - complètent le périmètre pour garantir qu'un environnement de remplacement peut être reconstitué dans les délais les plus courts possibles.

Sécurisation des sauvegardes
La sécurisation repose sur l'application du principe 3-2-1, standard reconnu de la gestion des sauvegardes : trois copies des données sont maintenues en permanence, sur deux supports de nature différente, dont une copie stockée hors site. Concrètement, cela se traduit par une copie sur le serveur de production, une copie sur le stockage objet OVHcloud Object Storage de type S3 dans une région géographique distincte, et une copie sur un support externe indépendant de l'infrastructure OVHcloud. Cette architecture garantit qu'aucun incident unique - défaillance matérielle, erreur humaine, cyberattaque - ne peut compromettre simultanément l'ensemble des copies.
L'ensemble des sauvegardes est chiffré au repos et en transit. Le chiffrement au repos utilise AES-256, standard industriel qui garantit que les données sont illisibles même en cas d'accès physique non autorisé au support de stockage. Le chiffrement en transit via TLS protège les sauvegardes lors de leur transfert vers le stockage objet distant.
Deux mécanismes de vérification complètent le dispositif. Une vérification d'intégrité hebdomadaire calcule et compare les checksums des sauvegardes pour détecter toute corruption silencieuse des données sauvegardées. Un test de restauration complet est réalisé avant le lancement officiel du jeu-concours, sur un environnement isolé, pour vérifier que la procédure de restauration est opérationnelle et que les données restaurées sont exploitables. Ce test de restauration est documenté et son résultat est consigné dans le journal de bord du projet : une sauvegarde dont la restauration n'a jamais été testée n'est pas une sauvegarde, c'est une illusion de sécurité.
Cohérence avec le workflow
Le choix d'un environnement Linux conteneurisé via Docker n'est pas dicté uniquement par les besoins du projet Thé Tip Top : il s'inscrit dans la transformation organisationnelle plus large que Furious Ducks engage en 2026, et constitue l'un des piliers de son nouveau workflow de production.
La cohérence entre les environnements est le premier bénéfice concret de cette approche. Chaque développeur travaille localement dans un environnement Docker identique à celui de staging et de production : mêmes versions de Node.js, de PostgreSQL, de Redis et de Traefik, mêmes variables d'environnement, mêmes configurations réseau. Cette parité stricte élimine la classe entière des bugs dits "ça marche sur ma machine" qui représentent une source de perte de temps considérable dans les équipes de développement travaillant sans conteneurisation. Elle garantit également que les tests exécutés localement par le développeur produisent exactement les mêmes résultats que ceux exécutés par le pipeline Jenkins, renforçant la fiabilité du processus de validation.
La maintenabilité de l'infrastructure est considérablement améliorée par la containerisation. Chaque service - API NestJS, base de données PostgreSQL, cache Redis, reverse proxy Traefik - est encapsulé dans son propre conteneur avec ses dépendances explicitement déclarées dans le fichier Docker Compose. Mettre à jour une version de PostgreSQL ou de Redis se résume à modifier un numéro de version dans un fichier de configuration et à relancer le conteneur concerné, sans risque d'impact sur les autres services. Cette indépendance entre les composantes de l'infrastructure réduit significativement la dette technique liée à la gestion des dépendances système.
La facilité de déploiement et de restauration est le troisième bénéfice direct. Un déploiement en production se résume à un docker-compose pull suivi d'un docker-compose up, une opération reproductible et réversible en quelques minutes. En cas d'incident nécessitant un rollback vers une version précédente, il suffit de relancer l'image Docker correspondant au dernier tag stable - une opération qui peut être effectuée en moins de cinq minutes sans intervention manuelle complexe sur le serveur. Cette réversibilité rapide est particulièrement précieuse dans le contexte d'une opération de soixante jours où chaque minute d'indisponibilité a un impact direct sur l'expérience des participants.
Enfin, la réduction des erreurs de configuration est une conséquence naturelle de l'approche Infrastructure as Code portée par Docker Compose. L'ensemble de la configuration de l'infrastructure est décrite dans des fichiers versionnés dans GitLab, relus lors des merge requests et protégés par le pipeline CI/CD. Une modification accidentelle ou non validée de la configuration ne peut pas atteindre la production sans avoir été revue et approuvée, éliminant les erreurs de configuration manuelle qui sont historiquement l'une des principales causes d'incidents en production.
Conclusion
Les choix techniques présentés dans cette section ne sont pas le résultat d'une liste de préférences technologiques, mais d'une réflexion cohérente construite autour des contraintes réelles du projet. Une opération de soixante jours, 500 000 codes à gérer, des pics de trafic imprévisibles, des données personnelles soumises au RGPD et une promesse de disponibilité totale pendant toute la durée du jeu-concours - ce contexte a dicté chaque décision, de la stack technique à la politique de sauvegarde en passant par le choix de l'hébergeur.
Ce qui ressort de l'ensemble de ces choix, c'est une logique de cohérence verticale. NestJS, PostgreSQL, Redis, Next.js et Docker ne sont pas des technologies choisies indépendamment les unes des autres : elles forment un écosystème full-TypeScript homogène, containerisé et testable à chaque niveau, dans lequel une modification sur une composante n'entraîne pas de rupture sur les autres. Cette cohérence est ce qui permettra au développeur lead de travailler seul sur la partie technique sans accumuler de dette organisationnelle, et à l'ensemble de l'équipe de reprendre le code à n'importe quel moment sans avoir à reconstituer un contexte trop fragmenté.
La stratégie de tests mérite d'être soulignée comme un choix structurant à part entière. Sur un projet où la mise en production ne peut pas être reportée - le premier jour de distribution des codes en boutique est une date contractuelle - l'absence d'un pipeline de validation automatisé serait une prise de risque inacceptable. Les cinq niveaux de tests, les quality gates SonarQube et les tests de performance K6 ne sont pas du perfectionnisme technique : ce sont les garde-fous qui permettent de livrer avec confiance dans un calendrier serré.
Enfin, l'hébergement OVHcloud, la stratégie de sauvegarde 3-2-1 et la politique de downscaling post-opération illustrent une dimension souvent négligée dans les projets de cette nature : la fin de vie du dispositif est pensée dès la conception. Thé Tip Top ne récupérera pas simplement un site qui fonctionne - il récupérera ses données dans des formats exploitables, une infrastructure documentée et une base de code maintenable. C'est ce que Furious Ducks entend par responsabilité client.
